# 2026-10-27 — DWC3: why every endpoint command timed out

**Symptom.** The USB driver probed, the core was found at `0x0A600000`, and then
every endpoint command failed:

```
SWEET USB: ep0 cmd 0x1 timeout
SWEET USB: DEPCFG timeout
```

No adb, no gadget, nothing on the host side. Three separate defects were hiding
behind that one symptom.

## 1. Not a DMA problem (ruled out)

The first suspicion was `pmap` — descriptor addresses handed to the core are
physical, and a wrong translation looks exactly like a dead core. Patch `0085`
prints the buffer virtual address, the `pmap_find_phys` result, and the value
programmed into the register:

```
SWEET USB: dma va 0xffffffe0c1a04000 pmap_find_phys 0x41a04000 dma pa 0x41a04000
```

Translation was correct, and the address was inside the window handed to XNU.
`pmap` is innocent.

## 2. The core reset never finished

`DCTL.CSFTRST` must self-clear. It stayed set, so the core was held in reset
while the driver issued commands. Reason: `GCTL.DSBLCLKGTNG` (bit 0) gates the
core's clock, and the previous code wrote `DCTL = 0x2` wholesale, which also
threw away the `0x00F00000` that ABL had left there.

Patch `0086` sets `GCTL |= 1` (disable clock gating) before triggering the reset,
preserves the rest of `DCTL`, and no longer treats a timeout as fatal:

```
SWEET USB: reset STUCK                  (before: STUCK, reset never completed)
SWEET USB: reset done                   (after 0086)
```

## 3. The core refused the device role (the real cause)

`GCTL.PrtCapDir` (bits 13:12) read `0b10` — **OTG**. In OTG the core does not
commit to a role until the ID pin says so, and ABL leaves the ID/vbus state in a
way that never selects peripheral. A core with no role accepts no endpoint
commands, which is precisely the `ep0 cmd 0x1 timeout` seen above: reset and
clock were fine, the core simply had nothing to configure.

Patch `0088` forces it:

```c
dwc_wr(GCTL, (gctl0 | 1u) & ~(3u << 12) | (1u << 12));   /* device */
```

and prints what the core reports afterwards:

```
SWEET USB: GSTS 0x7e800000 DCFG 0x00480408
SWEET USB: running (DSTS ...)
```

## Where it stands

Role forcing works, the core leaves reset and reports a live `GSTS`. Endpoint 0
setup still times out, so the next layer is the one below "device role":

- `DCFG.DevSpd` vs the speed `GUSB2PHYCFG` was left at by ABL (a mismatch stalls
  the first SETUP packet);
- `DCFG.DevAddr` / `DCTL.RunStop` ordering — the core must be out of
  `RunStop` before `DEPCFG`;
- VBUS/ID: with `PrtCapDir` forced, a stale `GUSB2PHYCFG.SusPHY` or a missing
  vbus session keeps the PHY suspended and nothing arrives.

All three are register-visible from the driver, so this is a print-and-read loop,
not a guess. `sweetusb=2` keeps the verbose path enabled.

## Lesson

Three independent failures produced one identical message. The reset fix alone
looked like progress but changed nothing observable, because the role fix is what
unblocks endpoint commands; and the role fix alone would have failed on a core
stuck in reset. Both had to land before `GSTS` showed `running`.
