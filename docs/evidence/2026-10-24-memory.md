# 2026-10-24 — How much of the 4 GiB can XNU actually have?

**Question.** The handset is a 4 GiB RMX1971 and the first working image gave
the kernel 2 GiB. Can it use all four?

**Answer.** No — 3.09 GiB is the hard ceiling, and only because XNU accepts a
single contiguous range.

## What the hardware reports

Live FDT pulled from the handset through TWRP (`/sys/firmware/fdt`, parsed with
`dtc`). DDR is continuous across both banks:

```
0x80000000 + 0x80000000   → 2 GiB, "DDR0"
0x1_00000000 + 0x7E2C0000 → 1.97 GiB, "DDR1"
   contiguous, top = 0x17E2C0000, total 3.97 GiB
```

The low bank is not free: `/reserved-memory` pins hyp, XBL, TZ, modem, adsp,
cdsp, qseecom, `ramoops` and `cont_splash`, and the highest fixed reservation is

```
kboot_uboot_logmem  0xB8200000 + 0x100000   → ends at 0xB8300000
cont_splash         0x9C000000 + 0x2300000  → 35 MiB, the ABL framebuffer
```

So the free tail of the low bank starts at `0xB8400000` (1 MiB of slack above
the log buffer, which is deliberate: the kernel's own early allocations walk
upward from the base and we did not want to sit flush against a carve-out).

## Why that limits XNU

`arm_vm_init()` builds the VM map from `boot_args.physBase` / `boot_args.physSize`
— one base, one size, no list. Those come from `/chosen`'s `dram-base` and
`dram-size` in the ADT, which `mkpayload` copies into the payload header. There
is no reserved-memory mechanism on this kernel: anything the firmware reserved
must simply be *outside* the window.

| Candidate window | Base | Size | Usable |
| --- | --- | --- | --- |
| Upper bank only (default) | `0x1_00000000` | `0x7E2C0000` | 1.97 GiB |
| Tail + upper bank (max) | `0xB8400000` | `0xC5EC0000` | 3.09 GiB |
| Anything below `0xB8400000` | — | — | collides with a carve-out |

`0x17E2C0000 - 0xB8400000 = 0xC5EC0000 = 3.09 GiB`. A full 4 GiB is impossible
without teaching the kernel to span two ranges or to subtract reservations,
which is a much larger change than a board file.

## What was implemented

- `configs/rmx1971.adt.py` takes `--phys-base` / `--mem-size`, and refuses
  (`SystemExit`) any window that runs past `0x17E2C0000` or starts below
  `0xB8300000`. An earlier hand-computed size of `0xC5F40000` was 512 KiB too
  large and would have silently overlapped the top of DDR — the guard is what
  caught it.
- 1 MiB is carved off the top for the panic ring (`/pram` +
  `/chosen/embedded-panic-log-size`). Without it the kernel stops right after
  `kdp_core zlib memory` with no output at all.
- The kernel binary is **not** rebuilt for a different window: physBase/memSize
  are boot arguments, and `mkpayload` re-resolves the chained fixups against
  whatever the ADT says. A 3.09 GiB image is one script run
  (`--phys-base 0xb8400000`).

## Status

The 3.09 GiB image builds (19,025,920 bytes) and has been flashed once, but the
boot was not observed end to end. Two failure modes to watch for, both of which
would mean a missed carve-out:

- a hang in `ml_static_mfree` / `pmap_bootstrap` during early VM setup;
- UFS DMA faults — the host driver programs descriptors with physical addresses
  and would be the first thing to touch memory the firmware still owns.

Evidence for the current default (2.01 GiB) is a clean boot to SpringBoard plus
a panic log that survives reboots, which is what the ring is for.
