# 2026-10-27 — The power key is not a gpio

**Symptom.** Volume up/down worked after the TLMM driver landed; the power key
did nothing at all. No HID event, no wake, no lock.

**Why the obvious approach fails.** On this platform the power key does not
reach the TLMM block. It is `KPDPWR_N`, an input of the PM660's **PON**
peripheral, which is an SPMI slave. There is no gpio to read and no interrupt
line the AP can latch early in boot.

## The SPMI path

The PMIC sits behind the Qualcomm SPMI arbiter (v5). Two register windows
matter, both mapped by `sweet_spmi`:

| Window | Address | Use |
| --- | --- | --- |
| arbiter core | `0x0C440000` | APID→PPID mapping table at `0x900 + 4n` |
| obs (EE0) | `0x0E600000` | per-APID command/data registers, stride `0x80` |

Per APID at `0x80 * apid`:

| Offset | Register |
| --- | --- |
| `0x00` | `CMD` |
| `0x08` | `STATUS` |
| `0x18` | `RDATA0` |

A read is issued by writing the SPMI address to `CMD` and polling `STATUS` until
the transaction completes, then taking the 8-bit result from `RDATA0`.

The address is encoded as `PPID = (sid << 8) | (addr >> 8)`. PON lives at
`sid 0, addr 0x800`, so `PPID = 0x08`.

## Finding the APID

One PPID can be reachable through several APIDs (different execution
environments were handed overlapping windows). The arbiter's table showed **three
candidates**; the only way to tell which one the AP has is to try them:

1. select the APID,
2. read `PON_RT_STS` (`0x810`) through it,
3. a valid transaction returns a plausible status bit, an unmapped one returns
   `STATUS = 0` forever.

`APID = 7` answered. `PON_RT_STS` bit 0 is `KPDPWR_N`, and it reads **1 while the
key is held** (active-high in the RT status, even though the pad is active-low).

```
SWEET PON: apid 3 -> timeout
SWEET PON: apid 5 -> timeout
SWEET PON: apid 7 -> rt_sts 0x00000001   (key down)
SWEET PON: apid 7 -> rt_sts 0x00000000   (released)
```

## Driver

`bsd/dev/sweet_pon.c` (part of patch 0082), polled from a kernel thread:

- 4 ms poll — a human press is tens of milliseconds, and the PON block has no
  interrupt we can hook this early;
- 3 identical frames before the state is accepted (debounce against SPMI read
  glitches);
- 120 ms lockout after an edge, so one press is one event;
- emits `sweet_hid_key(0, ...)` — the same path the volume keys use, so it
  arrives in SpringBoard as an ordinary HID key (`0x30` for power).

Two design constraints came out of this board:

1. **No allocations in the probe path.** The existing `sweet_spmi.c` called
   `IOLockAlloc` and returned NULL during early boot; every later caller then
   failed silently. The PON driver therefore has no locks, no buffers, no
   `IOMalloc` — a static state machine and MMIO reads only.
2. **Off by default in the boot-args.** `sweetpon=0` skips the driver, which is
   how it was proved that the HID event came from PON and not from a stray gpio.

## Result

Power press → lock screen off/on, and the key reaches SpringBoard as HID. Volume
keys unchanged (TLMM `gpio24` / `gpio92`, active-low, one step per press after
the same 3-frame debounce).

Register summary, as encoded in `board.toml [buttons]`:

```
spmi_arbiter_core = 0x0C440000
spmi_obs          = 0x0E600000     # EE0
power_ppid        = 0x08           # PON, sid 0, addr 0x800
power_rt_sts      = 0x810          # bit 0 = KPDPWR_N, 1 = pressed
```
